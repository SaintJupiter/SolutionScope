# SolutionScope v2.2：与普通 RAG 的边界及产品深化

## 结论

SolutionScope 仍然使用检索，但检索只负责提供候选证据。v2.2 的核心产品任务不是“根据材料回答问题”，而是判断：

> 每一项来源要求，是否被方案完整响应，并且是否存在可执行、可判定的验收方法。

因此，RAG 是底层能力之一，不是产品本身。若移除覆盖模型、证据角色隔离、生命周期判断、确定性放行门禁和要求变更影响，系统就会退化为普通知识库问答。

## 普通 RAG 能做什么

普通 RAG 擅长：

- 找到与问题相关的段落；
- 总结材料中提到的能力、指标和方法；
- 给回答附加引用；
- 在上下文充足时指出明显缺失或矛盾。

这些能力本身不能证明方案满足要求。例如，要求材料写有“识别率不低于 92%”，验收材料也写有“按 92% 判定”，但方案材料只写“支持目标识别”。普通 RAG 很容易把三段相关内容组织成一段完整回答；实际上，方案从未承诺达到该指标，不能进入验收。

## v2.2 增加的决策结构

### 1. 三类证据不可互相替代

| 证据角色 | 回答的问题 | 不能证明什么 |
| --- | --- | --- |
| 要求材料 | 应当达到什么 | 方案已经实现 |
| 方案材料 | 计划或当前实现了什么 | 验收方法可执行 |
| 验收材料 | 如何测试与判定 | 方案已经承诺满足要求 |

每条证据带有固定角色和定位。要求原文不能被用作方案覆盖证据，测试计划也不能替方案补写能力。

### 2. 把复合要求拆成最小可审查组件

每项要求被拆成：

- 要求动作；
- 适用条件；
- 每个量化指标；
- 预期测试方法；
- 验收判定口径。

模型只能逐组件判断 `covered / partial / absent / conflicting / unverifiable`，不能用一句“整体基本满足”掩盖局部缺口。

### 3. 区分方案评审和验收准备

- 在 `proposal_review` 中，明确标注为规划中的能力可以作为方案响应的一部分。
- 在 `acceptance_review` 中，`planned / candidate / unknown` 不得被当作当前已具备能力。

同一句“后续将支持多源时间同步”，在方案阶段可以算规划覆盖，在验收阶段必须阻断。这一规则由确定性程序执行，而不是交给模型临场发挥。

### 4. 放行结论由规则派生

模型只做组件级判断。最终状态由程序根据完整性、证据角色、生命周期和验收可执行性派生：

- `pass_with_evidence`
- `block_missing_solution`
- `block_missing_verification`
- `block_conflict`
- `human_review`

任何必选组件缺失、跨角色引用、证据越界或未解决冲突都会关闭放行门禁。

### 5. 原始输出与派生判断分离

原始模型输出保留不改写；结构校验、证据校验、聚合状态和人工审核包作为独立派生产物保存。这样可以回答“模型原来写了什么、程序因为什么阻断、人工最后改了什么”。

### 6. 要求变化会使旧结论失效

要求版本不是静态知识库。v2.2 将新旧原子要求按语义对齐，区分 `unchanged / modified / added / removed / split / merged`。除 `unchanged` 外，任何变化都会冻结原放行状态并要求重新核对方案响应、验收计划和人工确认。普通 RAG 即使能总结两个版本的差异，也不会天然维护这条决策依赖链。

### 7. 数值口径由程序复核，不接受模型自报“已覆盖”

v2.2 要求模型抄录方案和验收材料实际写出的指标对象、比较符、数值与单位，再由程序与要求原文逐项比较：

- 下限要求中，方案值低于要求值时阻断；
- 上限要求中，方案值高于要求值时阻断；
- `600 ms` 与 `0.6 s` 等可安全换算的单位先归一后比较；
- 指标对象不一致、单位不可比或材料没有给出实际阈值时转人工复核。

因此，“三段材料都提到了时延”仍不足以放行。系统检查的是方案承诺和验收阈值是否满足要求，而不只是是否召回相关文本。

## 当前已实现的产品闭环

```text
要求材料 ─┐
方案材料 ─┼→ 角色隔离的证据登记 → 要求原子化 → 分角色候选检索
验收材料 ─┘                                      ↓
                              逐组件覆盖判断 → 确定性聚合与放行门禁
                                                   ↓
                                    覆盖矩阵 / 缺口清单 / 人工审核包

旧要求原子 + 新要求原子 → 变更对齐 → 受影响方案与验收项 → 冻结旧结论 / 人工确认
```

v2.2 已实现：

- 三类分页材料的独立证据登记；
- BM25、指标匹配、状态词、短语重叠和邻段扩展组成的混合候选检索；
- 要求原子化及动作、条件、指标、验收组件拆分；
- 方案覆盖、验收可执行性和证据角色校验；
- 方案评审/验收准备两种生命周期门禁；
- 原始输出留存、确定性聚合和审查矩阵导出。
- 新旧要求的严格变更形状校验、放行冻结和三方复核清单。
- 量化指标的实际值抄录、单位归一、上下限比较与失败动作派生。

## 工程自测中的关键失败案例

合成自测故意构造了两类“看似相关、实际上不能放行”的材料：

1. 要求和验收计划均出现“识别率 ≥92%”，但方案未承诺该指标，也未限定工况；结果为方案部分覆盖并阻断。
2. 方案支持记录输入、输出时间戳，验收计划规定“时延 ≤600ms”，但方案未承诺 600ms；结果为验收方法可执行、方案仍不完整并阻断。

这两类判断无法由“检索到了相关段落”直接推出，必须同时区分证据角色、要求组件与覆盖状态。

## 尚未完成的部分

以下内容不能被现有实现夸大：

- 当前候选发现仍是轻量混合检索，尚未实现向量召回、学习式重排和大型文档增量索引；
- v2 已通过确定性工程自测，但尚无冻结保留集上的语义优势结果；
- 尚未形成专家一致性、实际审核时间或生产 ROI 证据；
- 覆盖判断仍需要模型参与，关键结论保留人工门禁。

因此目前可以声称“实现了不同于普通 RAG 的三方覆盖审查与确定性口径门禁”，不能声称“准确率优于 RAG”或“已替代专家评审”。

## 下一验证门槛

使用未参与开发的公开长篇技术材料，构造彼此独立的要求、方案响应和验收计划，冻结人工参考后，对比：

1. 普通检索增强的一次性回答；
2. SolutionScope v2.2 三方覆盖、确定性指标门禁与变更影响工作流。

分别报告关键要求召回、伪放行率、方案覆盖判断一致性、验收可执行性判断一致性和人工修改量。只有通过该对照，才能把 v2 的机制优势升级为效果结论。
