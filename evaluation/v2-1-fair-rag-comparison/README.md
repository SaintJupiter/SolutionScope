# SolutionScope v2.1 与普通 RAG 的公平对照协议

## 目的

验证受控覆盖审查是否比一次性检索增强回答更少漏掉原子要求、更少错误放行，并降低人工复核成本。该协议不以引用数量、输出长度或结构合同通过率代替语义质量。

## A/B 条件

| 条件 | A：一次性普通 RAG | B：SolutionScope v2.1 |
| --- | --- | --- |
| 输入 | 同一份要求、方案、验收材料 | 同一份要求、方案、验收材料 |
| 任务 | 一次回答各项要求是否覆盖并引用依据 | 原子化要求，分角色判断方案覆盖和验收可执行性，再由规则门禁 |
| 模型 | 与 B 相同的模型快照、推理等级和采样参数 | 与 A 相同 |
| 检索材料 | 同一来源登记表与同一检索候选预算 | 同一来源登记表与同一检索候选预算 |
| 调用成本 | 记录调用次数、输入输出 Token、时间 | 分别记录，不做等成本伪装 |
| 输出约束 | 相同的最终审核字段 | 额外保留组件判断与派生门禁，但评分映射到相同最终字段 |

`prepare-baseline` 只负责冻结 A 组请求；不得让 A 组看见 B 组输出、错误反馈或人工参考答案。

## 数据划分

1. 按完整文档划分开发集和保留集，禁止把同一材料的段落随机分到两侧；
2. 在两组模型输出生成前冻结问题、原子要求参考、评分规则和人工接管预期；
3. 保留集只执行一次，不因结果不好而继续改 Skill 或重跑；
4. 修改 Skill 后必须启用新的未见文档，旧保留集降级为开发诊断集。

## 主要指标

1. **原子关键要求召回率**：动作、条件、指标和验收口径是否被逐项保留；
2. **错误放行率**：方案或验收缺少关键组件时，系统是否错误给出通过；
3. **方案覆盖判断一致率**：`full / partial / absent / conflict` 与冻结参考是否一致；
4. **验收可执行性一致率**：方法、阈值、条件能否形成可判定测试；
5. **变更影响召回率**：修改、拆分、合并后的要求是否触发相应复核任务；
6. **人工修改量与审核时间**：审核者为得到可用结论需要改多少字段、花多长时间。

证据定位正确率和结构合同错误单独报告，不能与上述语义指标合并为一个总分。

## 失败条件

出现以下任一情况，本轮不得用于“效果优于 RAG”的外部表述：

- A/B 输入、检索预算、模型或评分口径不一致；
- 参考答案在任一组输出前未冻结；
- B 组引用了未分配给该要求的证据而未经人工复核；
- 任一组存在结构错误却通过派生修复掩盖原始失败；
- 只有开发集、没有未见文档保留集；
- 提升仅来自更多调用，却没有披露调用次数和成本。

## 可公开的结论边界

- 工程自测可以说明机制按设计工作；
- 冻结开发集可以作为迭代诊断，但不能证明泛化；
- 只有通过一次性未见文档保留集，才报告该材料上的描述性差异；
- 未获得多材料和独立复核前，不使用“准确率提升”“替代专家”或“生产可用”等表述。
